## High-level summary

compact-js 3.0.1-rc.0 repoints the ledger 9 era at the bindings for ledger 9.1.0.2-rc.0 —
`@midnightntwrk/ledger-v9` 1.0.2-rc.0 over `@midnightntwrk/onchain-runtime-v4` `^4.0.0-rc.3`
(resolving 4.0.1), the same range `@midnight-ntwrk/compact-runtime` 0.21.0 requests.
Nothing in compact-js's own API moves, and contracts compiled for the ledger 9 era on 3.0.0 run
unchanged. This is a release candidate built on release-candidate ledger bindings, so it is for
testing against ledger 9.1.0.2-rc.0 rather than for production use.

## Audience

These notes are written for:

- Developers building DApps on the `@midnight-ntwrk/compact-js` packages.

- Shielded Technologies engineering teams maintaining consuming SDKs.

## Dependencies

- Still requires compactc 0.36 for contracts executed on the ledger 9 era; 3.0.0's recompilation
  requirement is unchanged and no further recompilation is needed to take this release.
- Still requires an ESM-capable consumer.
- Pairs with ledger 9.1.0.2-rc.0. The ledger binding is a release candidate, so the fee and
  gas-accounting behaviour it carries can still change before the stable 9.1.0.2.
- The ledger 8 era (`/v8`, `/v8/effect`) is untouched.

**Downstream impact (cascading effects).** A consuming SDK or DApp taking this release inherits
the 1.0.2-rc.0 ledger binding for its ledger 9 path and should pin to it deliberately rather than
through a range, so the binding cannot move underneath an already-tested build. Consumers holding
both eras in one process keep their ledger 8 artefacts as they are.

## Improvements

### Ledger 9 moves to the `1.0.2-rc.0` binding line

**Description**: Ledger 9 moves to the `1.0.2-rc.0` binding line. The era now builds against
`@midnightntwrk/ledger-v9` `1.0.2-rc.0` over `@midnightntwrk/onchain-runtime-v4` `^4.0.0-rc.3` —
the range `@midnight-ntwrk/compact-runtime` `0.21.0` itself requests, so the pair shares one
on-chain runtime instance rather than loading a second. These are the bindings for ledger
9.1.0.2-rc.0, which partitions transcripts against a mock transaction's
size and time-to-dismiss and rehearses calls with the widest commitment tree indices. The
binding adds `TransactionShape` and an optional expected-shape argument to
`partitionTranscripts`; neither is re-exported through the `Ledger` facade, so compact-js's own
API is unchanged. The ledger 8 era is untouched. (commit ddd493b)

## Known issues

All three were open at 3.0.0 and remain open at this release.

### Verifier-key removal transactions are rejected with `BalanceCheckOverspend`

**Description**: a maintenance transaction that removes a verifier key fails the balance check
although the ledger bindings report it as paid, which affects the `v4` maintenance updates built
by `ContractExecutable` ([midnight-node issue #2375](https://github.com/midnightntwrk/midnight-node/issues/2375)).

**Workaround (if any)**: none in compact-js — the fix is in the ledger's fee calculation and
reaches consumers when they pick up the ledger release that carries it.


### `CompiledContract` context fails across identical package copies

**Description**: when two identical copies of a compiled contract package are resolved in one
process, building a contract context fails with a raw constructor `TypeError`
([compact-js issue #28](https://github.com/midnightntwrk/compact-js/issues/28)).

**Workaround (if any)**: deduplicate the contract package so a single copy is resolved.

### A valid null `--input-ps` is rejected

**Description**: the CLI's `circuit` command rejects a valid null `--input-ps`, so a contract
whose initial private state is `null` cannot be run from the CLI
([compact-js issue #30](https://github.com/midnightntwrk/compact-js/issues/30)).

**Workaround (if any)**: give the contract a non-null initial private state.
